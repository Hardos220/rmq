# Руководство для ИИ-агентов: очередь вычислений `rmq`

Это полное руководство. Прочитай его целиком перед первым тяжёлым запуском в сессии: несколько минут чтения
экономят часы ожидания и не мешают владельцу ПК. Вывести его снова можно командой `rmq guide`.

## 0. Коротко

1. Любые тяжёлые вычисления запускай только через `rmq`, никогда напрямую. Это правило по умолчанию, спрашивать
   разрешения не нужно.
2. Сначала `rmq top` (сколько свободно), потом `rmq run …` (до ~8 минут) или `rmq submit …` (дольше) с честной заявкой
   `--cpu --ram --vram --time`.
3. Не жди дольше лимита своего инструмента: опрашивай `rmq wait <id> --timeout 540`. Код 124 значит «ещё работает».
4. Долгие и GPU-задачи пиши с чекпоинтами и ставь `--preempt requeue`. Появился файл из `RMQ_STOP_FILE` —
   сохрани чекпоинт и заверши процесс.
5. Если этот ПК занят, а в вычислительной сети есть свободные ПК (`rmq nodes`), долгую самодостаточную задачу можно
   отправить туда: `rmq submit --where auto …`. Папка проекта уедет туда, созданные файлы вернутся сами.
6. Ожидание в очереди и пауза — норма: владелец ПК всегда важнее. Ничего не обходи и не трогай сам менеджер.
7. Пачку тяжёлых кусков ставь одной серией (`--series ИМЯ`): пойдут по одной. Заявку сверяй с прошлыми запусками
   (`rmq past`), статистика и история нагрузки — `rmq stats`, `rmq history` (раздел 10).

## 1. Что это за система

Это компьютер владельца, и он пользуется им одновременно с тобой: работает, смотрит видео, играет. Кроме тебя,
вычисления запускают и другие агенты. Менеджер ресурсов (RMQ) — очередь, которая запускает задачи агентов только
на свободных ресурсах:

- **Программы владельца менеджер не трогает и всегда пропускает вперёд.** Задачи агентов работают с самым низким
  приоритетом процессора (Idle), диска и памяти.
- **Пул для задач** — всё, что не заняли Windows и программы владельца, минус небольшой резерв (5% свободного, но не
  меньше 1 ГБ ОЗУ и 1 потока CPU).
- **Если владельцу понадобилась память, задачи сразу замораживаются**, а их память выгружается на диск. Когда
  ресурсы освобождаются, задачи сами продолжают с того же места.
- **Во время игры** GPU-задачи на паузе (если владелец не выбрал режим «Продуктивность»: тогда их останавливает
  только его загрузка видеокарты выше 40%), а CPU-задачи работают только на энергоэффективных E-ядрах.
- **Между агентами ресурсы делятся честно:** никто не может занять всё на сутки, а маленькие задачи не ждут
  за огромными.
- **Железо берегут.** Когда ноутбук греется, регулятор температуры плавно урезает задачам процессор, а при перегреве
  все задачи замораживаются до остывания. Если на системном диске остаётся меньше 10 ГБ, задачи замораживаются, пока
  место не освободят.
- **Пропало питание.** Если настольный ПК перешёл на ИБП, задачи с `--preempt requeue` сохраняют чекпоинт и
  останавливаются, остальные замораживаются, новые не стартуют — до возвращения сети. Ноутбука на своей батарее это
  не касается.

Железо этого ПК: {HARDWARE}. Актуальные свободные ресурсы всегда показывает `rmq top`. Обычно ОС и программы
владельца занимают значительную часть ОЗУ, поэтому задачам доступно меньше, чем есть в ПК.

Если этот ПК состоит в вычислительной сети с другими ПК (`rmq nodes`), задачи можно отправлять и туда (раздел 11).

## 2. Когда использовать `rmq`

**Обязательно через `rmq`** — всё, что подходит хотя бы под один пункт:

- идёт дольше ~1 минуты;
- использует больше 2 потоков CPU (многопроцессность, BLAS на все ядра, `make -j`, параллельные сборки);
- берёт больше ~2 ГБ ОЗУ;
- использует GPU (CUDA, PyTorch/TensorFlow/JAX на видеокарте);
- запускается сериями: перебор параметров, кросс-валидация, бенчмарки.

Примеры: обучение и инференс моделей, симуляции (Монте-Карло, МКЭ, молекулярная динамика), численное решение
уравнений, оптимизация, обработка больших датасетов, рендеринг, тяжёлые сборки C++/Rust.

**Как обычно, без `rmq`:** git, установка пакетов, линтеры и форматтеры, юнит-тесты на секунды, просмотр файлов,
мелкие скрипты и проверки, которые завершаются за секунды и почти не грузят ПК.

**Не запускай через `rmq`:** интерактивные программы (у задачи нет ввода с клавиатуры), долгоживущие сервисы
(Jupyter, веб-серверы, TensorBoard) и программы с окнами. Если такое нужно — спроси пользователя.

Если сомневаешься, используй `rmq`: накладные расходы около секунды.

## 3. Где команда и как проверить, что всё работает

- Git Bash: `{RMQ_SH}`
- cmd и PowerShell: `{RMQ_CMD}`
- Дашборд владельца: {URL}

Ниже везде написано просто `rmq` — подставляй полный путь. Ключи не нужны: `rmq` сам определяет, какой ты агент
(«инструмент@проект», например `claude-code@my-project`), и менеджер регистрирует тебя при первой задаче.

```bash
rmq whoami     # каким агентом тебя видит менеджер и твои лимиты
rmq top        # загрузка ПК и сколько ресурсов доступно задачам прямо сейчас
rmq queue      # очередь и выполняющиеся задачи всех агентов
rmq stats      # статистика менеджера за 7 дней: нагрузка, задачи, температуры, по дням и по агентам
```

Если `rmq` отвечает «менеджер ресурсов не отвечает» (код выхода 3), запусти его: `rmq start`. Это безопасно:
команда только поднимает менеджер в фоне. Если и это не помогло — сообщи пользователю, что нужно открыть ярлык
«Менеджер ресурсов» на рабочем столе.

## 4. Как оценить ресурсы — честная заявка

Заявка решает, когда задача стартует и насколько она защищена. Завышенная заявка заставляет ждать тебя и мешает
другим, заниженная делает задачу первой кандидаткой на заморозку.

### CPU — `--cpu N`

`N` — сколько потоков задача реально использует одновременно.

| Сценарий | `--cpu` |
|---|---|
| обычный однопоточный Python-скрипт | 1 |
| numpy / scipy / scikit-learn с BLAS | сколько хочешь дать BLAS: `OMP_NUM_THREADS` и подобные выставятся сами |
| `multiprocessing.Pool(k)`, `joblib n_jobs=k` | k (бери `k = int(os.environ["RMQ_CPU"])`) |
| PyTorch на CPU | N, и в коде `torch.set_num_threads(int(os.environ["RMQ_CPU"]))` |
| `make -j k`, `cmake --build . -j k`, `cargo build -j k` | k |
| Julia | N и `julia --threads=N` |

- **Нужен весь процессор** (ПК простаивает, задача хорошо параллелится) — заявляй все потоки (их число — в
  `rmq top`). Заявка больше свободного означает «дай всё свободное»: задача стартует и получает весь пул (всё, кроме
  средней нагрузки владельца и его резерва 5%). Ставь в задаче столько же потоков (`RMQ_CPU` подскажет заявку).
- **Процессор делится, а не захватывается.** Задаче с небольшой заявкой CPU не нужно ждать, даже если весь процессор
  занят: работающие задачи ужимаются, в сумме не больше чем на четверть. Это относится и к твоим собственным задачам:
  GPU-задача с `--cpu 4` стартует рядом с твоей же задачей на весь процессор. Если придёт другой агент, CPU сразу
  делится поровну между агентами, а твоя задача продолжает работать на своей доле, без заморозки. Когда другой
  закончит, доля вернётся. Замораживают только из-за памяти.
  **Исключение — когда пул сжимается.** Во время игры владельца задачам остаются только E-ядра (пул уменьшается
  примерно вдвое), регулятор температуры тоже урезает пул. Если работающие задачи уже занимают такой пул с запасом
  больше четверти, новые — даже однопоточные — ждут, пока какая-то закончится или игра кончится: ужимать работающие
  сильнее менеджер не станет. В причине ожидания так и написано: «идёт игра владельца: задачам доступны только
  E-ядра…».
- CPU жёстко ограничен долей задачи. Лишние потоки сверх доли только толкаются между собой, поэтому не ставь потоков
  больше заявки.
- Во время игры владельца задачам доступны только энергоэффективные E-ядра (на процессорах без них — половина потоков):
  задача идёт медленнее, а время с урезанным процессором в сверхурочные не идёт.
- **Плавный старт.** Только что запущенная или возобновлённая задача сначала получает около 30% заявленного
  процессора, и за ~1,5 минуты (так по умолчанию, владелец может изменить) доля плавно растёт до заявки: охлаждение успевает, температура не скачет, а регулятор
  не раскачивает нагрузку. Встраивать свой плавный старт в задачу не нужно.

### ОЗУ — `--ram`

Заявляй пиковое потребление с запасом ~20%. Форматы: `8`, `8G`, `512M`.

- **numpy:** массив занимает «число элементов × размер элемента» (float64 — 8 байт). Матрица 10 000 × 10 000 float64 —
  0,8 ГБ, а временные копии при операциях легко удваивают пик.
- **pandas:** CSV в памяти обычно в 2–5 раз больше файла.
- **Обучение на CPU:** параметры × 4 байта × ~4 (веса, градиенты, два состояния Adam) плюс активации батча.
- **multiprocessing:** каждый воркер получает свою копию данных — умножай.
- **Надёжнее всего пилотный запуск** на малой части данных (`rmq run --time 5m …`): в итоге будет «пик ОЗУ»,
  он же в `rmq status <id>`.
- **Менеджер подскажет по истории.** При постановке он сравнивает заявку с твоими прошлыми запусками той же команды
  (числа в аргументах не в счёт: `--part 3` и `--part 17` — одна команда) и предупреждает, например: «в прошлых
  запусках этой команды (5) пик ОЗУ был до 200 МБ, а заявлено 2 ГБ: с завышенной заявкой задача дольше ждёт память».
  Завышенная ОЗУ — частая причина лишнего ожидания. Прошлые запуски целиком: `rmq past --name chunk` (время, пик ОЗУ,
  сколько ядер задача реально занимала).
- **Если задача выросла сверх заявки,** её не убивают. Но при нехватке памяти её заморозят первой, а при
  перезапуске она будет ждать свой реальный пик.

### Видеопамять — `--vram`

- Указывай, только если задача использует GPU. Без `--vram` задача **не видит CUDA** (`CUDA_VISIBLE_DEVICES=""`):
  `torch.cuda.is_available()` вернёт `False`.
- **Оценка:** веса модели (fp32 — 4 байта на параметр, fp16/bf16 — 2) + состояния оптимизатора (Adam — ещё 2 × fp32)
  + активации (растут с размером батча) + ~0,5 ГБ на контекст CUDA.
- **PyTorch:** ограничь себя сам:
  `torch.cuda.set_per_process_memory_fraction(float(os.environ["RMQ_VRAM_GB"]) / (torch.cuda.get_device_properties(0).total_memory / 2**30))`.
- **TensorFlow и JAX:** «рост памяти» включён, а предвыделение выключено автоматически.
- **Игры владельца важнее.** Когда владельцу не хватает видеопамяти, GPU-задачу сначала замораживают, а затем
  останавливают и перезапускают позже (если владелец не выключил это: тогда её только замораживают). Поэтому
  GPU-задачам нужны чекпоинты.

### Время — `--time`

- Реалистичная оценка чистого времени работы, без очереди и пауз. Форматы: `90s`, `15m`, `2h`, `1d`, `1h30m`.
  По умолчанию 1 час.
- **Как оценить:** запусти долю работы (одну эпоху, 1% данных), умножь и добавь 30%.
- **Короткие задачи идут раньше.** Задача до 30 минут, которой мешает «захватчик», через 2 минуты ожидания может
  его потеснить.
- **Задача, работающая дольше заявленного +10%, становится «сверхурочной»:** у неё меньше очков, её легко
  вытеснить, а занятые ресурсы засчитываются твоему агенту вдвойне. Не занижай время. Время, когда задаче давали
  меньше заявленного процессора (игра владельца и E-ядра, регулятор температуры, деление с другими агентами,
  плавный старт), в сверхурочные не идёт: `rmq status` показывает его как «с урезанным процессором».
- **Не завышай время:** длинная заявка — меньше очков и меньше шансов проскочить вперёд.
- `--time-limit` — жёсткий лимит: по его истечении задача убивается. Используй как защиту от зависаний.
- **Поправить заявку на ходу:** настоящую длительность долгая задача узнаёт только после старта. Если по её прогрессу
  видно, что заявки не хватит, поправь её, пока задача не стала сверхурочной: `rmq retime <id> --time 5h` (новая
  длительность от старта). Изменение пишется в журнал, владелец его видит — завышать «на всякий случай» не нужно.

### Нагрев: та же работа — меньше тепла (расчёты на видеокарте)

ПК владельца — часто ноутбук: процессор и видеокарта охлаждаются общими тепловыми трубками. Тепло — это
потраченная энергия. Если твой расчёт делает ту же работу за меньшее число джоулей, ПК меньше греется,
регулятор температуры реже урезает задачи, а сама задача обычно ещё и заканчивается раньше. Больше всего это
касается расчётов на видеокарте: она легко берёт 70 Вт и больше.

**Это рекомендации.** Если задаче действительно нужно иначе — например, без `float64` не обойтись или важна полная
скорость, — можно от них отступить, но скажи об этом пользователю: что именно и почему.

**Сначала — сделать работу дешевле.** Это даёт больше всего:

- **Считай пачкой, а не циклом.** Независимые запуски (сиды, параметры, варианты модели) складывай в одну
  операцию с измерением «батч» (`torch.bmm`, векторизация numpy) вместо цикла по ним. Видеокарта, загруженная
  тысячами крошечных операций, показывает 99% загрузки и берёт полную мощность, а полезной работы делает мало.
  Пачка делает в разы больше работы почти за ту же мощность.
- **Проверь точность чисел.** На игровых видеокартах (GeForce) `float64` в десятки раз медленнее `float32`, а
  видеокарта при этом жарит на полную. Где точности хватает — `float32` (или TF32/bf16 для нейросетей); то, что
  требует `float64`, часто выгоднее считать на процессоре.
- **Не синхронизируйся без нужды.** `.item()`, `.cpu()`, печать значений внутри цикла заставляют ждать
  видеокарту на каждом шаге. Копи результаты на видеокарте и забирай их кусками.
- **Длинный цикл из мелких операций** ускоряют CUDA Graphs или `torch.compile`: накладные расходы на запуск
  операций падают в разы.
- **Проверь, нужна ли видеокарта.** Для маленьких матриц пачка на процессоре бывает почти так же быстра, а ядро
  процессора берёт единицы ватт против десятков у видеокарты. Прогони 1% работы там и там и сравни время.
- **Меньше лишних запусков:** сначала грубая сетка параметров, потом уточнение; плохие варианты отсекай рано;
  повторяющиеся куски кэшируй.

Сколько энергии ушло на задачу, видно в `rmq status <id>` («энергия») и в `energy_wh` файла условий: так можно
сравнить версии кода.

**Если ПК всё равно горячий — сбавь темп ровно, а не рывками.** Делай после каждого шага короткую паузу:
несколько миллисекунд, не больше 50. За такие паузы температура не успевает меняться, и для железа это просто
ровная нагрузка поменьше. Паузы по секунде и дольше вредны: кристалл каждый раз остывает и снова нагревается,
а такие тепловые циклы изнашивают пайку и сам чип. «Шаг» здесь — кусок работы на 10–100 мс. Если шаг длиннее,
делай паузы между частями шага.

Понять, горячий ли ПК и виновата ли в этом видеокарта, можно по полю `heat` файла условий (раздел 8): оно показывает
нагрев прямо сейчас. Регулятор температуры умеет урезать только процессор, поэтому, если греет видеокарта, помочь
может только сама GPU-задача. А если процессор греется от чужой работы, сбавлять темп бесполезно. Образец, который
сам подстраивает темп:

```python
import json, os, time
import torch

share = 1.0                          # доля времени, когда видеокарта занята; 1.0 — без пауз
last_check, cool_since = time.monotonic(), time.monotonic()

def heat():
    try:
        with open(os.environ["RMQ_CONDITIONS_FILE"], encoding="utf-8") as f:
            return json.load(f).get("heat")
    except (KeyError, OSError, ValueError):
        return None                  # не под rmq или файл ещё не появился

for step in range(n_steps):
    t0 = time.perf_counter()
    ...                              # шаг расчёта на видеокарте (кусок на 10–100 мс)
    torch.cuda.synchronize()         # один раз за шаг
    busy = time.perf_counter() - t0
    if share < 1.0:
        time.sleep(min(0.05, busy * (1 / share - 1)))
    if time.monotonic() - last_check >= 30:          # раз в полминуты: не видеокарта ли греет ПК
        last_check, h = time.monotonic(), heat()
        if h and h["factor"] < 1 and (h["by"] == "gpu" or (h["gpu_heat_share"] or 0) >= 0.5):
            share, cool_since = max(0.4, share - 0.1), time.monotonic()
        elif time.monotonic() - cool_since >= 300:   # 5 минут спокойно
            share = min(1.0, share + 0.1)
```

Паузы короче миллисекунды не получатся: на Windows `time.sleep` точен примерно до 1 мс в Python 3.11 и новее,
в старых версиях — до 15 мс.

## 5. Запуск

### `rmq run` — короткие задачи (до ~8 минут)

```bash
rmq run --cpu 4 --ram 8 --time 10m -- python analyze.py --input data.csv
```

Ставит задачу, ждёт старта и печатает лог в stdout, а служебные сообщения — в stderr. Код выхода равен коду
задачи. Если ожидание оборвётся (например, по таймауту твоего инструмента), задача **продолжит работу** — дождись
её через `rmq wait <id>`. Ctrl+C в терминале отменяет задачу. Параметр `--timeout N` ограничивает ожидание,
по истечении — код 124.

### `rmq submit` — всё, что дольше

```bash
id=$(rmq submit --cpu 8 --ram 16 --vram 6 --time 3h --preempt requeue --name train-v2 -- python train.py --epochs 30)
echo "задача $id"
```

Печатает номер задачи в stdout (удобно сохранить в переменную) и сразу возвращает управление.

### Все параметры

| Параметр | Смысл | По умолчанию |
|---|---|---|
| `--cpu N` | потоков CPU | 1 |
| `--ram G` | пик ОЗУ, ГБ | 2 |
| `--vram G` | видеопамять, ГБ; 0 — GPU не виден | 0 |
| `--time T` | ожидаемое время работы | 1h |
| `--time-limit T` | жёсткий лимит, после него задача убивается | нет |
| `--priority low\|normal\|high` | `low` — фоновая задача, уступает всем; `high` — только с кодовым словом владельца (ниже) | normal |
| `--code СЛОВО` | кодовое слово владельца для высокого приоритета | — |
| `--preempt suspend\|requeue` | что делать, когда ресурсы нужны владельцу: заморозить или остановить и перезапустить позже | suspend |
| `--name NAME` | короткое понятное название для дашборда | имя скрипта |
| `--cwd DIR` | рабочая папка | текущая |
| `--env K=V` | доп. переменная окружения (можно несколько) | — |
| `--no-env` | не передавать своё окружение | окружение передаётся |
| `--shell` | выполнить команду одной строкой через cmd.exe | — |
| `--series NAME` | серия: из задач одной серии работает одна за раз, по порядку постановки | — |
| `--after ID` | запуск только после успешного окончания задачи ID (иначе эта отменяется) | — |
| `--where PC\|auto` | выполнить на другом ПК сети (раздел 11); там же `--files`, `--results`, `--requirements` | этот ПК |

Команда пишется после `--`. Всё, что после `--`, относится к твоей программе.

### Высокий приоритет — только по кодовому слову владельца

Задача с высоким приоритетом стартует сразу: задачи пониже замораживаются, чтобы освободить ей место (раздел 12).
Поэтому он есть у агента, только если **владелец сам назвал тебе своё кодовое слово** в разговоре:

```bash
rmq submit --priority high --code СЛОВО --cpu 4 --ram 2 --time 10m -- python urgent.py
rmq priority 215 high --code СЛОВО     # поднять уже поставленную задачу (low / normal — без слова)
```

- Используй слово только для той работы, для которой владелец его дал. Не ищи его в файлах и настройках, не
  подбирай, не записывай в файлы, коммиты, память и логи: агентам оно не видно, а каждое неверное слово владелец
  видит в журнале. После 5 неверных за час высокий приоритет для тебя закрывается на час.
- Без слова или с неверным словом задача всё равно ставится — с обычным приоритетом, а `rmq` пишет почему.
- Серия и `--after` соблюдаются и при высоком приоритете.

### Примеры

```bash
# Python-скрипт и модуль
rmq run --cpu 2 --ram 4 --time 15m -- python scripts/clean.py data/raw.csv
rmq submit --cpu 8 --ram 12 --time 2h --name fit-xgb -- python -m mypkg.train --config cfg.yaml

# окружения: активированный venv/conda наследуется; без активации — путь к его python (от --cwd) или conda run
rmq submit --cpu 4 --ram 8 --time 1h -- .venv/Scripts/python.exe sim.py
rmq submit --cpu 4 --ram 8 --time 1h -- conda run -n sci python sim.py

# GPU
rmq submit --cpu 4 --ram 16 --vram 8 --time 4h --preempt requeue --name finetune -- python finetune.py

# R, Julia, скомпилированная программа
rmq run --cpu 1 --ram 3 --time 20m -- Rscript analysis.R
rmq submit --cpu 8 --ram 6 --time 3h -- julia --threads=8 model.jl
rmq submit --cpu 16 --ram 24 --time 6h -- ./build/solver.exe --mesh fine.msh

# конвейеры и перенаправления — через bash -c
rmq run --cpu 2 --ram 2 --time 10m -- bash -c "python gen.py | python consume.py > out/result.txt"
```

Пути внутри задачи — обычные пути Windows. Относительные пути считаются от рабочей папки (`--cwd`, по умолчанию
та, где ты вызвал `rmq`), в том числе путь к самой программе (`.venv/Scripts/python.exe`, `./build/solver.exe`).

### Порядок задач: `--series` и `--after`

```bash
# серия: из задач одной серии работает одна за раз, по порядку постановки (остальные ждут своей очереди)
for k in 0 1 2 3; do rmq submit --series chunks --cpu 8 --ram 4 --time 40m --name "chunk-$k" -- python run.py --part $k; done

# после другой задачи: старт только после её успешного окончания; если она не удалась — эта отменяется
a=$(rmq submit --cpu 8 --ram 8 --time 1h -- python prepare.py)
rmq submit --after $a --cpu 4 --ram 4 --time 30m -- python analyze.py
```

Серия — лучший способ поставить пачку тяжёлых кусков: они не мешают друг другу и не раскачивают ПК, а очередь
сама подаёт следующий. Серия считается внутри твоего агента; `--series` и `--after` работают и с `--where`
(следующая задача уезжает на тот ПК, только когда предыдущая закончилась).

## 6. Ожидание, таймауты инструментов, логи

У инструментов агентов есть лимит времени на команду. Например, у Bash в Claude Code — до 10 минут. Поэтому
для всего, что дольше нескольких минут:

```bash
id=$(rmq submit ... -- python train.py)
rmq wait $id --timeout 540   # 0 = готово, 124 = ещё работает, иное = код ошибки задачи
```

- **Код 124** значит, что задача ещё не закончилась. Займись другой работой или снова вызови `rmq wait`.
  Опрашивай не чаще раза в 30–60 секунд — для долгих задач реже.
- **Если инструмент умеет фоновые команды,** `rmq wait $id` можно запустить в фоне.
- **Несколько задач сразу:** `rmq wait 12 13 14 --timeout 540` ждёт, пока закончатся все. Код выхода — 0, если все
  успешны, иначе код первой (в порядке перечисления) неуспешной; 124 — ещё не все закончились.
- **Менеджер ненадолго недоступен** (ПК спал, менеджер перезапускается или обновляется): `rmq wait` и `rmq run`
  не сдаются, а ждут дальше до своего `--timeout`. Если менеджер так и не ответил — код 124 (задача никуда не делась,
  подожди ещё); код 3 — только если менеджер не отвечал с самого начала.
- **`rmq logs $id --tail 100`** — последние строки лога: stdout и stderr вместе. Строки `[rmq …]` пишет менеджер
  (старт, перезапуск, код выхода).
- **`rmq logs $id -f`** следит за логом до завершения задачи и блокирует, поэтому помни про таймаут инструмента.
- **`rmq status $id`** показывает состояние, причину ожидания, текущее потребление, время работы, прогресс,
  колебания нагрузки и условия счёта. `rmq status $id --events` — ещё и все события задачи (старт, паузы и их причины,
  перезапуски, сон ПК, изменение заявки). `rmq status $id --json` удобно разбирать.
- **Прогноз.** `rmq status` и `rmq queue` пишут, когда задача примерно стартует и закончится («старт ~15:40, конец
  ~16:30»; в JSON — `forecast`: `start`, `end`, `basis`). Менеджер проигрывает очередь вперёд по прошлым успешным
  запускам тех же команд, иначе — по заявке, у работающей — по прогрессу. Это оценка: игра владельца, пауза или новые
  задачи её сдвигают. Честный `--time` и прогресс делают её точнее.
- **Результаты пиши в файлы,** а не только в stdout: лог ограничен по размеру (256 МБ) и хранится 12 месяцев.

**Прогресс задачи** владелец видит в дашборде и в `rmq status`, с оценкой оставшегося времени. Сообщить его можно
двумя способами:

- **Автоматически.** Если задача рисует прогресс-бар `tqdm`, менеджер сам читает «45/100» и описание бара из лога.
  Делать ничего не нужно.
- **Явно.** Записывай в файл из переменной `RMQ_PROGRESS_FILE` одну строку: `сделано/всего пояснение`
  (например `37/120 эпоха 3`) или `45%`. Подойдёт любой язык. Обновляй не чаще раза в несколько секунд.
  Пример на Python:

  ```python
  import os
  def report(done, total, note=""):
      path = os.environ.get("RMQ_PROGRESS_FILE")
      if path:
          try:
              with open(path, "w", encoding="utf-8") as f:
                  f.write(f"{done}/{total} {note}")
          except OSError:
              pass  # прогресс — подсказка, а не повод падать
  ```

**Две оценки оставшегося времени.** Первая — по доле выполненного («45% за 20 минут — осталось ~25»). Вторая — по
скорости за последние 10 минут работы. Если они сильно расходятся, `rmq status` и дашборд показывают обе: так видно и
неправильно посчитанный прогресс (90% при реальных 93 из 420), и медленную фазу. «Прогресс не менялся N мин» —
задача за последние 10 минут работы не продвинулась.

Явный файл важнее бара в логе. При перезапуске задачи с начала старый прогресс сбрасывается. Обновление прогресса —
ещё и признак работы: задачу, которая 30 минут ничего не делает, менеджер замораживает как зависшую (раздел 7).

Коды выхода `rmq`:

| Код | Значение |
|---|---|
| 0 | задача завершилась успешно |
| код задачи (1–255) | задача завершилась с ошибкой, смотри лог |
| 2 | ошибка запроса (неверный параметр, нет команды и т.п.) |
| 3 | менеджер не запущен (и не ответил до конца `--timeout`) → `rmq start` |
| 124 | ожидание закончилось по `--timeout`, задача продолжает работу |
| 130 | ожидание прервано (Ctrl+C) |

## 7. Состояния задачи и что делать

| Состояние | Что значит | Что делать |
|---|---|---|
| в очереди | ждёт ресурсов; место и причина — в `rmq status` | ждать; при необходимости уменьшить заявку |
| выполняется | работает | ждать |
| на паузе | заморожена: процесс стоит, память выгружена | ничего; продолжит сама с того же места |
| готово | код 0 | забрать результаты |
| ошибка | код ≠ 0 | читать лог, исправлять |
| отменена | отменена тобой или владельцем | — |
| лимит времени | убита по `--time-limit` | увеличить лимит или ускорить |
| потеряна | процесс пропал, пока менеджер был выключен | поставить заново |
| зависла | 30 минут не было признаков работы — задачу заморозили | посмотреть лог; продолжить — `rmq resume <id>`, отменить — `rmq cancel <id>` |

Частые причины ожидания и паузы:

- **«Не хватает ресурсов — ОЗУ: нужно X, свободно Y».** Пул занят. Жди или уменьши заявку, если она завышена.
- **«мало места в файле подкачки».** Виртуальная память ПК почти заполнена. Уменьши `--ram` или сообщи пользователю.
- **«У агента уже N активных задач».** Достигнут твой лимит: дождись своих задач или отмени ненужные.
- **«Агент уже занимает больше своей доли».** Ты занимаешь больше честной доли, а другие ждут. Дождись освобождения.
- **«Ресурсы копятся для давно ждущей задачи #N».** Пропускаются только задачи, которые успеют закончиться раньше.
- **«Серия «…»: ждёт, пока закончится задача #N»**, **«Ждёт, пока успешно закончится задача #N»** — так задумано
  (`--series`, `--after`). Если задача, после которой эта должна идти, не удалась, эта отменяется с пояснением.
- **«…Идёт игра владельца: задачам доступны только E-ядра, а их уже занимают работающие задачи».** Новая стартует,
  когда какая-то закончится или игра кончится (раздел 4).
- **«Игровой режим», «Видеокарта занята вами».** Владелец играет или занят GPU. Ждут только GPU-задачи, иногда часами.
  Не обходи это: просто сообщи пользователю.
- **«Оперативная память отдана вашим приложениям».** Владельцу понадобилась память, задача заморожена.
- **«Уступила ресурсы задаче #N (честная очередь)».** Задачу потеснили по правилу честности. Она продолжит позже.
- **«Уступила место задаче #N с высоким приоритетом».** Владелец (или агент, которому он это разрешил) поставил
  задачу с высоким приоритетом, и ей понадобилась память. Твоя задача заморожена и продолжит сама, когда место
  освободится.
- **«Перезапущена с начала: …».** Процесс остановили (так бывает с `--preempt requeue` и с GPU-задачами).
  Задача снова в очереди и при старте начнёт сначала, поэтому продолжай с чекпоинта.
- **«Пауза всех задач», «Менеджер был выключен».** Это решение владельца, жди.
- **«Перегрев: задачи агентов заморожены, пока ПК не остынет».** Какой-то компонент ноутбука перегрелся. Все задачи
  стоят, пока процессор, плата, видеокарта и SSD не остынут до нормы и не пробудут там 2 минуты. Обычно это минуты,
  после этого задачи продолжат сами, сначала на половине процессора. Если перегрев повторяется, уменьши `--cpu`.
- **Регулятор температуры.** Пока компоненты теплее своих целей, регулятор плавно урезает задачам процессор (бывает
  до 20% от их доли). Задача просто идёт медленнее, делать ничего не нужно.
- **«Мало места на диске».** На системном диске (или на диске, где работает задача) свободно меньше 10 ГБ. Задачи
  стоят, пока место не освободят. Если большие файлы пишет твоя задача, удали лишнее или сообщи пользователю.
- **«Пропало питание, ПК работает от ИБП».** Владелец без электричества, ПК держит ИБП. Задачи с `--preempt requeue`
  сохраняют чекпоинт и останавливаются (раздел 9), остальные заморожены, новые не стартуют. Через минуту после
  возвращения сети всё продолжится само. Если ИБП разрядится раньше, замороженные задачи пропадут вместе с ПК, а задачи
  с чекпоинтом продолжат с него. Поэтому долгим задачам и нужны чекпоинты.
- **«Сохраняет чекпоинт и останавливается».** Задаче с `--preempt requeue` создали файл `RMQ_STOP_FILE` (раздел 9).
  Через минуту её остановят принудительно, затем она встанет в очередь.
- **«Зависла».** Задача 30 минут не грузила процессор и видеокарту, не писала в лог и на диск, а прогресс не
  менялся, — менеджер её заморозил. Сама она не продолжит. Посмотри `rmq logs <id>`: не ждёт ли она ввода, сети или
  блокировки. Если задача просто долго ждёт чего-то внешнего, продолжи её (`rmq resume <id>`) и обновляй
  `RMQ_PROGRESS_FILE` хотя бы раз в 10 минут — это считается признаком работы. Если зависла по-настоящему —
  `rmq cancel <id>`, исправь причину и поставь заново.

Пока выполняются задачи, ПК не уходит в сон по таймеру. Но владелец может сам усыпить его или закрыть крышку
ноутбука: тогда задача просто встанет и продолжит после пробуждения, а время сна ей не засчитается. Ничего делать не
нужно.

**Отменять свою задачу не обязательно**, если она ждёт, стоит на паузе или мешает другой твоей задаче:
- пауза снимется сама;
- процессор менеджер ужимает сам (до четверти у работающих задач), так что небольшая новая задача стартует рядом —
  кроме времени, когда пул сжат игрой или регулятором (раздел 4).

Это твои задачи — решай сам. Просто учти, что при отмене пропадает прогресс задачи, а поставленная заново задача
встаёт в конец очереди.

## 8. Окружение задачи

- Задача получает твоё окружение: PATH, активированный venv/conda, переменные. Рабочая папка — та, где ты вызвал
  `rmq`, или `--cwd`.
- **Ввода с клавиатуры нет.** `input()` упадёт. Всё передавай аргументами и файлами.
- **Окон нет.** Графики сохраняй в файлы. `MPLBACKEND=Agg` выставлен заранее, `plt.show()` ничего не открывает.
- **Все дочерние процессы принадлежат задаче:** их замораживают и останавливают вместе с ней. Через 10 секунд
  после завершения главного процесса оставшиеся дочерние убиваются, поэтому не запускай фоновых «демонов».
- **Задача работает с самым низким приоритетом CPU, диска и памяти.** Когда владелец активен, она медленнее — это
  нормально. Когда ноутбук греется, регулятор температуры плавно урезает задачам процессор, а при перегреве они
  замораживаются до остывания.

Переменные, которые выставляет менеджер:

| Переменная | Значение |
|---|---|
| `RMQ_TASK_ID` | номер задачи |
| `RMQ_CPU`, `RMQ_RAM_GB`, `RMQ_VRAM_GB` | твоя заявка — используй их для настройки потоков и памяти |
| `RMQ_RESTART_COUNT` | сколько раз задача перезапускалась с начала (0 — первый запуск) |
| `RMQ_PROGRESS_FILE` | файл для прогресса: `сделано/всего пояснение` или `45%` (см. раздел 6) |
| `RMQ_STOP_FILE` | если этот файл появился — сохрани чекпоинт и заверши процесс (см. раздел 9) |
| `RMQ_CONDITIONS_FILE` | условия, в которых задача считает: паузы, сон, урезанный процессор, игра, соседи (см. ниже) |
| `RMQ_TASK_DIR` | служебная папка задачи (там лог); результаты храни у себя в проекте |
| `RMQ_URL` | адрес менеджера |
| `OMP_NUM_THREADS`, `MKL_NUM_THREADS`, `OPENBLAS_NUM_THREADS`, `NUMEXPR_NUM_THREADS`, `NUMBA_NUM_THREADS`, `RAYON_NUM_THREADS`, `POLARS_MAX_THREADS`, `JULIA_NUM_THREADS` | = `--cpu` (если ты не задал их сам) |
| `CUDA_VISIBLE_DEVICES=""` | если не указан `--vram` |
| `TF_FORCE_GPU_ALLOW_GROWTH=true`, `XLA_PYTHON_CLIENT_PREALLOCATE=false` | если указан `--vram` |
| `PYTHONUNBUFFERED=1`, `PYTHONIOENCODING=utf-8`, `MPLBACKEND=Agg` | живой лог в UTF-8, без окон графиков |

### Замеры времени: `RMQ_CONDITIONS_FILE`

Если задача сама меряет время (бенчмарк, выигрыш по скорости), замер может испортить то, чего изнутри не видно:
заморозка, сон ПК, работа только на E-ядрах во время игры владельца, регулятор температуры, соседние задачи. Менеджер
раз в 10 секунд пишет в файл из `RMQ_CONDITIONS_FILE` (JSON) накопленные с первого старта задачи секунды:

| Поле | Что это |
|---|---|
| `run_s`, `wall_s` | время работы и время от первого старта по часам (с паузами и сном) |
| `paused_s`, `slept_s` | была заморожена; ПК спал |
| `held_s` | получала меньше заявленного процессора (игра, регулятор, деление с другими, плавный старт) |
| `ecores_s`, `game_s` | только E-ядра; владелец играл |
| `throttled_s` | регулятор температуры урезал задачам процессор |
| `shared_s`, `max_neighbours` | рядом работали другие задачи; сколько их было больше всего |
| `owner_cpu_avg` | сколько ядер в среднем занимал владелец |
| `energy_wh` | энергия процессора и видеокарты, пришедшаяся на задачу, Вт·ч (оценка: их мощность делится по доле времени, которое задача их занимала); `null`, если мощность не измерялась |
| `cpu_power_w`, `clock_p_ghz`, `clock_e_ghz` | средняя мощность процессора (Вт) и средняя частота P- и E-ядер (ГГц), пока задача работала; `null`, если на ПК нет датчика (LibreHardwareMonitor). У процессора без E-ядер частота всех ядер — в `clock_p_ghz` |
| `clean` | всё перечисленное (кроме игры, владельца, мощности и частот) — ноль |
| `heat` | нагрев **прямо сейчас** (не накопленный): `factor` — какую долю заявленного процессора регулятор температуры оставляет задачам (1 — не урезает); `by` — какой компонент он держит у цели (`cpu`, `board`, `gpu`, `ssd` или `null`); `state` — `normal`, `warm` (регулятор урезает) или `hot` (перегрев, всё заморожено); `temps` и `targets` — температуры и цели, °C; `cpu_power_w`, `gpu_power_w` — мощность процессора и видеокарты; `gpu_heat_share` — доля видеокарты в их общей мощности (`null`, если что-то не измеряется). GPU-задаче стоит сбавить темп, если `factor` < 1 и `by` = `gpu` или `gpu_heat_share` ≥ 0,5 (раздел 4, «Нагрев») |

Прочитай файл перед замером и после него: если разница во всех полях — ноль, замер чистый; иначе пометь его как
грязный или повтори. Мощность и частоты на чистоту не влияют, но объясняют разницу между чистыми замерами: ноутбук
может работать в режиме 45 Вт или 100 Вт, и при 45 Вт ядра идут заметно медленнее. Сравнивай замеры при близкой
частоте или пересчитывай на неё. Файл появляется через ~10 секунд после старта. Те же поля — в `rmq status <id>` («условия
счёта») и в `rmq status <id> --json` (`conditions`).

```python
import json, os, time

def conditions():
    try:
        with open(os.environ["RMQ_CONDITIONS_FILE"], encoding="utf-8") as f:
            return json.load(f)
    except (KeyError, OSError, ValueError):
        return None   # не под rmq или файл ещё не появился

before = conditions(); t0 = time.perf_counter()
...                                    # замеряемая часть
elapsed = time.perf_counter() - t0; after = conditions()
keys = ("paused_s", "slept_s", "held_s", "ecores_s", "throttled_s", "shared_s")
clean = before and after and all(after[k] - before[k] < 1 for k in keys)
```

Файл обновляется раз в 10 секунд: для коротких замеров (меньше минуты) прочитай его ещё раз через 10 секунд после
конца замера.

## 9. Чекпоинты и `--preempt requeue`

- **`--preempt suspend` (по умолчанию).** При нехватке ресурсов процесс замораживается и потом продолжает с той же
  инструкции. Это безопасно для любой задачи. Но если владельцу понадобится видеопамять, замороженную GPU-задачу всё
  равно остановят и перезапустят с начала.
- **`--preempt requeue`.** При нехватке процесс останавливают сразу, а позже запускают с начала. Память освобождается
  мгновенно, и такие задачи легче пропускают вперёд. Твой код должен уметь продолжать с чекпоинта.

Ставь `--preempt requeue` и сохраняй чекпоинты для задач дольше ~30 минут и для всех GPU-задач. Образец на Python:

```python
import os, pickle, time

CKPT = "checkpoints/run1.pkl"          # в папке проекта, не в RMQ_TASK_DIR
os.makedirs("checkpoints", exist_ok=True)

state = {"step": 0, "result": None}
if os.path.exists(CKPT):
    with open(CKPT, "rb") as f:
        state = pickle.load(f)
    print(f"продолжаю с шага {state['step']} (перезапуск №{os.environ.get('RMQ_RESTART_COUNT', '0')})", flush=True)

def save(state):
    tmp = CKPT + ".tmp"
    with open(tmp, "wb") as f:
        pickle.dump(state, f)
    os.replace(tmp, CKPT)              # атомарно: чекпоинт никогда не бывает полузаписан

last = time.monotonic()
for step in range(state["step"], 100_000):
    ...                                # работа
    state["step"] = step + 1
    if time.monotonic() - last > 300:  # раз в 5 минут
        save(state)
        last = time.monotonic()
save(state)
```

Для PyTorch то же самое: `torch.save({"model": model.state_dict(), "opt": opt.state_dict(), "epoch": epoch}, tmp)`,
затем `os.replace(tmp, path)`, а при старте `torch.load(path)` и продолжение с `epoch + 1`.

### Мягкая остановка: `RMQ_STOP_FILE`

Иногда задачу с `--preempt requeue` нужно остановить не срочно: уступить честной очереди, освободить память, пока
её нехватка ещё не критическая, или сохранить работу, когда пропало питание и ПК держится на ИБП. Тогда менеджер
создаёт файл по пути из переменной `RMQ_STOP_FILE` и ждёт до 60 секунд.

- Проверяй этот файл между шагами, раз в несколько секунд: проверка дешёвая.
- Файл появился — сохрани чекпоинт и заверши процесс (код выхода любой). Задача встанет в очередь и при следующем
  запуске продолжит с чекпоинта.
- Не успела за 60 секунд — задачу остановят принудительно, как если бы файла не было.
- Если работа в этот момент уже закончена, ничего страшного: при перезапуске код увидит готовый результат и быстро
  выйдет.
- Когда ресурсы нужны владельцу срочно (критическая нехватка памяти, видеопамять для игры), задачу останавливают
  сразу. Поэтому периодические чекпоинты нужны всё равно.

```python
import os, sys

STOP = os.environ.get("RMQ_STOP_FILE")

for step in range(state["step"], 100_000):
    ...                                # работа
    state["step"] = step + 1
    if STOP and os.path.exists(STOP):  # менеджер просит освободить ресурсы
        save(state)
        sys.exit(0)
```

## 10. Параллелизм и серии задач

- **Одна задача с N потоками или N задач?** Тесно связанную работу (одна модель, одна симуляция) делай одной задачей
  с внутренним параллелизмом. Независимые прогоны (перебор параметров, сиды, фолды) — отдельными задачами.
- **У агента есть лимиты:** по умолчанию не больше 4 задач одновременно и 100 в очереди. Свои смотри в `rmq whoami`.
  Остальные задачи просто подождут.
- **Перебор параметров:** ставь каждую конфигурацию отдельно с понятным `--name`, сохраняй номера и жди их все.
  Если конфигурации тяжёлые (каждая на весь процессор), ставь их одной серией (`--series sweep`): пойдут по одной.

  ```bash
  ids=""
  for lr in 0.1 0.03 0.01; do
    ids="$ids $(rmq submit --cpu 2 --ram 3 --time 20m --name "sweep-lr$lr" -- python train.py --lr $lr)"
  done
  rmq wait $ids --timeout 540; echo "код $?"      # 124 — ещё не все; повтори
  ```
- **Не ставь сотни крошечных задач.** Объединяй их в батчи, чтобы каждая задача работала хотя бы 1–2 минуты.
- **Перед повторной постановкой проверь `rmq queue`:** может, такая задача уже есть.

### Статистика менеджера: `rmq stats`

Сколько процессорного времени ушло на задачи, сколько их завершилось и с какими ошибками, как грелся ПК, когда
регулятор урезал задачи и когда владелец играл — по часам или дням и по агентам. Полезно, чтобы оценить заявку
(`--time`, `--cpu`) по прошлым запускам или выбрать время для большой серии.

```bash
rmq stats                    # за 7 дней, этот ПК
rmq stats --period 24h       # за сутки по часам (ещё 30d и all)
rmq stats --pc Стационар     # другой ПК из «Моих ПК» владельца; --pc all — все его ПК вместе
rmq stats --json             # всё как есть, для разбора программой
```

### Нагрузка по времени: `rmq history`

То же, что графики дашборда, но текстом: сколько процессора брали владелец и задачи, память, температура, мощность
и частота процессора (если есть датчик), игра и регулятор — по отрезкам за выбранный срок. С `--task` — сколько ядер и памяти брала именно эта задача и не
колебалась ли её нагрузка.

```bash
rmq history --range 6h                 # весь ПК за 6 часов (до 30 дней: --range 30d)
rmq history --task 12 --range 2h       # одна задача: ядра сред/макс, ОЗУ, колебания
rmq history --pc Стационар --range 1h  # другой ПК из «Моих ПК» владельца
```

**Колебания нагрузки.** Если процессор задачи то загружен, то почти простаивает волнами, `rmq status`, `rmq queue` и
`rmq history --task` пишут «колеблется 0,9–8,5 яд., период ~1,5 мин». Обычно это фазы ожидания: проверка после
каждого куска, блокировка, диск или сеть, пул, которому не хватает работы. Задача идёт дольше, чем могла бы, а ПК
то греется, то остывает — стоит посмотреть, нельзя ли совместить фазы.

### Что менеджер хранит и как это получить

| Что | Сколько хранится | Как получить |
|---|---|---|
| итоги по часам: сколько шли расчёты, процессор и видеокарта задач, температуры, мощность и частоты процессора и видеокарты, энергия (оценка), регулятор, заморозки, игра, диск, число задач | всегда | `rmq stats` (по дням или часам), `rmq stats --file hourly.csv` |
| то же по агентам и часам | всегда | `rmq stats` (раздел «по агентам»), `rmq stats --file agents_hourly.csv` |
| каждая завершённая задача: ожидание, время работы, заявка, сколько ядер реально занимала, пик ОЗУ и VRAM, перезапуски, условия счёта, мощность и частоты процессора | всегда | `rmq past` (`--name`, `--command`, `--all-agents`), `rmq stats --file tasks.csv` |
| графики дашборда поминутно: нагрузка владельца и задач, память, видеокарта, температуры, мощность и частоты процессора, режимы | 12 месяцев | `rmq stats --file minutes-2026-10.csv` (список — `rmq stats --files`) |
| графики дашборда: точки раз в секунду / раз в 15 секунд / средние за 5 минут, с долей каждой задачи | 1 час / сутки / 30 дней | `rmq history --range 1h…30d`, `rmq history --json` |
| задача целиком: лог, события, условия счёта, прогресс; журнал событий менеджера | 12 месяцев после окончания | `rmq status <id> --events`, `rmq logs <id>` |
| другие ПК из «Моих ПК» владельца | на каждом ПК своё | `--pc ИМЯ` у `stats`, `history`, `queue`, `top`, `status`, `logs`; `rmq stats --pc all` — все вместе |

Задачу, отправленную на другой ПК владельца, статистика считает там, где она работала (в общей статистике она не
двоится). Всё это только для чтения: читай через `rmq`, сами файлы в папке менеджера не трогай. Описание колонок
CSV — `rmq stats --file README.txt`.

## 11. Вычислительная сеть: другие ПК

Владелец может объединить этот ПК со своими другими ПК («Мои ПК») и с ПК друзей, на которых стоит такой же менеджер
(через Tailscale — закрытую зашифрованную сеть). Тогда задачи можно отправлять и туда. На ПК владельца задача идёт как
своя, на ПК друга — гостем (ограничения ниже). `rmq nodes` помечает ПК владельца как «мой ПК».

```bash
rmq nodes          # ПК сети: на связи ли, принимает ли задачи, железо и сколько свободно прямо сейчас
rmq submit --where auto --cpu 8 --ram 16 --time 3h --name sweep -- python sweep.py   # где свободнее
rmq submit --where ivan-pc --cpu 4 --ram 8 --time 1h -- python train.py               # на конкретный ПК
```

- **Когда отправлять.** Долгие самодостаточные расчёты, когда этот ПК занят или ему не хватает ресурсов (например,
  нужна видеокарта, которой здесь нет). `--where auto` выбирает ПК, где задача стартует сразу, сначала среди ПК
  владельца; если такого нет — ставит её здесь. Без `--where` задача всегда выполняется на этом ПК.
- **Что уезжает.** Папка проекта: файлы git-репозитория (отслеживаемые и новые, без игнорируемых), а если это не
  репозиторий — папка без `.venv`, `.git`, `node_modules` и кэшей. Не больше 1 ГБ. Отправить только нужное:
  `--files "*.py" --files data/small.csv`. Не отправляй секреты: код и данные окажутся на чужом ПК.
  **Файлы уезжают при отправке** — сразу после постановки (у задачи серии или с `--after` — когда подойдёт её
  очередь), а не при старте на том ПК. Исправил код после постановки — отмени поставленные задачи и поставь заново:
  иначе они стартуют со старым кодом.
- **Крупные файлы — один раз.** Файлы от 256 КБ, которые тот ПК уже получил с этого ПК для прошлых задач (сверка по
  SHA-256), повторно не пересылаются: хозяин берёт их из своего кэша. Поэтому серия задач с одним датасетом стартует
  быстро уже со второй задачи. Изменённый файл — это новый файл, он уедет заново. Кэш живёт неделю с последнего
  использования.
- **Зависимости.** Если в папке есть `requirements.txt` (или указан `--requirements`), ПК-хозяин один раз создаст
  для них окружение Python и будет переиспользовать его. Первый запуск поэтому дольше. На хозяине своя версия
  Python — не полагайся на пакеты, которых нет в `requirements.txt`.
- **Что возвращается.** Когда задача закончится, все созданные и изменённые ею файлы (или только `--results
  results/`) вернутся в ту же папку проекта на этом ПК, по тем же относительным путям. Лог задачи — тоже. Так же и при
  отмене (`rmq cancel`): задача сначала останавливается там, потом сюда приходит всё, что она успела создать
  (чекпоинты в том числе), и её лог — пока она отменяется, `rmq status` пишет «отменяется». Если тот ПК не на связи,
  задача отменяется сразу, а её файлы остаются там (и удаляются через 72 часа).
- **Ограничения на другом ПК.** Используй только относительные пути внутри проекта: твоих абсолютных путей там нет.
  Ниже — ограничения ПК друга; на ПК владельца задача работает с обычными правами, но тоже в своей папке.
  Задача работает с пониженным уровнем доступа Windows: писать можно только в своей папке, файлы хозяина менять
  нельзя. Из переменных окружения доступны только системные и те, что передал через `--env K=V`. Окон и ввода
  нет, как и здесь.
- **Приоритет.** На чужом ПК задача стоит в общей очереди с низким приоритетом: хозяин и его агенты первые. Хозяин
  может закрыть свой ПК для сети — тогда задача встанет на паузу («владелец закрыл свой ПК для сети») и продолжит,
  когда он откроет его снова. Если ждать не хочется, отмени её и поставь на другой ПК.
- **Скорость и связь.** `rmq nodes` пишет, во сколько раз дольше там идут те же команды (по задачам, которые
  выполнялись и здесь, и там), и как Tailscale соединяет ПК: напрямую или через ретранслятор. `--where auto` отправляет
  задачу на более медленный ПК, только если там она закончится раньше, чем здесь после очереди.
- **ПК «не в сети».** `rmq nodes` пишет и причину, если менеджер её нашёл (например, «Tailscale видит тот ПК, но
  туннель между ПК не устанавливается»). Чинит это владелец: передай ему причину, сам ничего не меняй.
- **Слежение — как обычно.** `rmq status <id>` показывает «на ivan-pc: выполняется», `rmq wait`, `rmq logs`,
  `rmq cancel` работают так же. Номер задачи — номер на этом ПК.
- **Другие ПК владельца — целиком, только чтение.** `rmq queue --pc Стационар` — вся очередь того ПК (видно, например,
  свою же лишнюю задачу там), `rmq top --pc …` — его ресурсы, `rmq status <id> --pc …` и `rmq logs <id> --pc …` —
  задача там (номер — тамошний), `rmq history --pc …` и `rmq stats --pc …` — его нагрузка и статистика. Работает для
  «Моих ПК» владельца; у ПК друзей видны только сведения из `rmq nodes`.

## 12. Как устроен планировщик

- **Порядок очереди — по очкам:**
  `очки = 1000 × приоритет (низкий 0, обычный 0,5, высокий 1) + 500 × честная доля агента + 300 × ожидание +
  150 × короткость + 100 уже начатым − 500 сверхурочным`.
  - Честная доля = 2^(−(доля агента в недавнем потреблении) / (доля его веса)): 1 — агент давно не пользовался ПК,
    меньше — пользовался много. Потребление затухает вдвое за 12 часов.
  - Ожидание растёт линейно до 1 за 4 часа.
  - Короткость: 1 для задач ≤ 5 минут, 0 для ≥ 24 часов, логарифмически между ними.
  - Высокий приоритет — у задач владельца и у задач агента, которому владелец назвал своё кодовое слово
    (раздел 5). Без него агентам доступны «обычный» и «низкий».
- **Старт:** задача стартует, если её заявка (а для перезапускаемой — её реальный пик) помещается в свободную часть
  пула, не превышен лимит агента и не ждёт она свою серию или задачу из `--after`. Первые ~1,5 минуты процессор новой
  задачи плавно растёт до заявки (плавный старт).
- **Процессор:** делится по долям. Сначала задачи высокого приоритета, затем обычного, затем низкого. Внутри
  приоритета CPU делится поровну между агентами (по весу), а у агента — между его задачами; кому нужно меньше, получает
  сколько просил. Незанятое делится на всех. Агент, который занимает меньше своей доли, стартует сразу: остальным
  уменьшают долю, никого не замораживая.
- **Честное деление памяти:** каждому агенту с задачами положена доля пула по весу (поровну), по самому занятому
  ресурсу, с допуском 5 процентных пунктов. Пока другой агент ждёт, агент сверх доли не может занимать нужную ему
  память.
- **Вытеснение:** задача, которая ждёт дольше 2 минут (короткая, до 30 минут) или 10 минут (остальные), может
  заморозить задачи агента сверх его доли или сверхурочные задачи. Защиты от вытеснения:
  - первые 20 минут после запуска или возобновления задачу не трогают;
  - высокий приоритет защищает только задачу, которая укладывается в заявленное время;
  - агент, который сам превысит долю, вытеснять не может — пока его задача не прождёт больше часа (антиголодание).
- **Высокий приоритет не ждёт:** задаче с высоким приоритетом (её ставит владелец или агент с его кодовым словом)
  задачи с более низким приоритетом освобождают место сразу — замораживаются без ожидания и без защиты первых 20
  минут. Серии и `--after` соблюдаются.
- **Резервирование:** если первая в очереди задача ждёт больше 20 минут, вперёд неё пропускаются только задачи,
  которые по заявке закончатся раньше, чем для неё освободится место.
- **Владелец сильнее всех правил.** Нехватка памяти, игра, ручная пауза, перегрев и нехватка места на диске
  останавливают задачи независимо от очков.

Практический вывод: честные заявки и короткие задачи стартуют быстрее всего, а попытки «захватить» ПК
бессмысленны — такие задачи замораживают в пользу других.

## 13. Запрещено

- Запускать тяжёлые вычисления напрямую, в обход `rmq`, в том числе «быстрый тест», который на деле тяжёлый.
- Останавливать, перезапускать или настраивать менеджер, менять его режимы. Исключение — `rmq start`, когда он не
  запущен. Нельзя трогать файлы в его папке (`data/`, `settings.json`, `admin_token.txt`) и использовать админ-токен.
- Задавать `RMQ_AGENT`, чтобы выдать себя за другого агента или «обнулить» свою долю.
- Отменять чужие задачи (это и не получится).
- Опрашивать статус чаще раза в ~10 секунд; держать `rmq run` или `logs -f` дольше лимита своего инструмента.
- Заявлять ресурсы с большим запасом «на всякий случай».
- Запускать через очередь интерактивные программы, долгоживущие серверы, программы с окнами.

## 14. Общение с пользователем

- После постановки задачи сообщи пользователю номер, название, заявку и оценку времени, а также ссылку
  {URL}/#task=<номер>.
- Если задача долго ждёт, объясни причину из `rmq status` (например: «владелец играет — GPU-задачи на паузе»).
- После завершения сообщи результат, время работы и пиковую память.
- Обратись к пользователю, если:
  - менеджер не запускается;
  - твой агент отключён;
  - задаче нужно больше, чем ПК может дать в принципе;
  - она вечно ждёт из-за «мало места в файле подкачки».

## 15. Разбор проблем

| Симптом | Причина и решение |
|---|---|
| «менеджер ресурсов не отвечает» (код 3) | `rmq start`; если не помогло — попроси пользователя открыть ярлык «Менеджер ресурсов» |
| «агент … отключён владельцем ПК» | остановись и сообщи пользователю |
| «уже N задач в очереди (лимит)» | дождись или отмени свои ненужные задачи |
| «рабочая папка не существует» | исправь `--cwd` |
| код 127, «failed to start: [WinError 2]» | программа не найдена: проверь PATH и окружение; путь к программе считается от `--cwd`; `.sh` запускай через `bash script.sh` |
| «отменена: задача #N, после которой она должна была идти, завершилась без успеха» | `--after` ждёт только успешного окончания: исправь причину и поставь обе заново |
| задача долго «в очереди» с запасом ОЗУ | посмотри `rmq past` и предупреждения при постановке: завышенная заявка ОЗУ — частая причина ожидания |
| `ModuleNotFoundError` | задача запустилась не тем Python: активируй окружение до вызова `rmq` или укажи полный путь к python окружения; не используй `--no-env` |
| `MemoryError`, `std::bad_alloc`, «Unable to allocate» | увеличь `--ram` или уменьши батч или данные в памяти |
| `torch.cuda.is_available()` = False | добавь `--vram` |
| `CUDA out of memory` | уменьши батч или модель, проверь `rmq top`: видеопамять может быть занята владельцем |
| задача «потеряна» | менеджер перезапускался, и процесс пропал — поставь задачу заново |
| «мало места в файле подкачки» долго | уменьши `--ram` или сообщи пользователю |
| задача работает очень медленно | владелец активен (Idle-приоритет), идёт игра (только E-ядра) или ноутбук греется (регулятор температуры урезал процессор) — это нормально |
| «зависла» в `rmq status` | задача 30 минут ничего не делала и заморожена: проверь `rmq logs`, не ждёт ли она ввода, сети или блокировки; ложная тревога — `rmq resume`, зависла — `rmq cancel` |
| «Мало места на диске» | освободи место (удали лишние результаты своей задачи) или сообщи пользователю |
| лог пустой, хотя задача работает | Python буферизует вывод: `PYTHONUNBUFFERED` уже стоит; в других языках сбрасывай буфер (`flush`) |

## 16. HTTP API (если нет shell)

Адрес: {URL}. Каждый запрос должен представлять агента заголовком `X-RMQ-Agent: <инструмент>@<проект>` (URL-кодировка
для не-ASCII), тело — JSON с заголовком `Content-Type: application/json`.

| Запрос | Что делает |
|---|---|
| `POST /api/tasks` | поставить задачу. Тело: `{"argv": ["python", "x.py"], "cwd": "C:\\work", "cpu": 4, "ram": 8, "vram": 0, "time": "2h", "name": "x", "preempt": "requeue", "env": {...}}`, по желанию `"series": "S"`, `"after": 12`, `"priority": "high"` с `"priority_code": "СЛОВО"`; вместо argv можно `"command": "строка для cmd.exe"`. На другой ПК сети: `"where": "auto"` или имя ПК, плюс по желанию `"files"`, `"results"`, `"requirements"`, `"env_extra"`. Ответ: `{"id": 12, "warnings": [...]}` |
| `GET /api/tasks/<id>` | состояние задачи (`state`, `wait_text`, `reason_text`, `used`, `run_s`, `exit_code`, …) |
| `GET /api/tasks/<id>/log?offset=0&limit=65536` | кусок лога; `offset` с минусом — с конца; в ответе новый `offset` |
| `POST /api/tasks/<id>/cancel` | отменить свою задачу |
| `POST /api/tasks/<id>/resume` | продолжить свою замороженную задачу (например, «зависла») |
| `GET /api/state` | загрузка ПК, пул, все задачи |
| `GET /api/whoami` | твоё имя и лимиты |
| `GET /api/guide` | это руководство |
| `GET /api/nodes` | ПК вычислительной сети: связь, режим, железо, свободные ресурсы |
| `POST /api/tasks/<id>/time` | поправить заявку времени: `{"time": "5h"}` |
| `POST /api/tasks/<id>/priority` | поменять приоритет своей задачи: `{"priority": "normal"}`; высокий — `{"priority": "high", "code": "СЛОВО"}` |
| `GET /api/stats?period=7d&pc=` | статистика (как `rmq stats --json`); `pc` — имя другого ПК владельца или `all` |
| `GET /api/stats/files/<имя>` | CSV-файл статистики (`hourly.csv`, `agents_hourly.csv`, `tasks.csv`, `minutes-ГГГГ-ММ.csv`, `README.txt`) |
| `GET /api/metrics?range=3600&since=0` | точки графиков (как `rmq history --json`), до 30 дней |
| `GET /api/tasks?mine=1&limit=100` | задачи (последние 12 месяцев), `mine=1` — только твои |
| `GET /api/home/<ПК>/state`, `/metrics`, `/tasks/<id>`, `/tasks/<id>/log` | то же для другого ПК из «Моих ПК» (только чтение) |

```bash
curl -s -X POST {URL}/api/tasks -H "X-RMQ-Agent: my-tool@my-project" -H "Content-Type: application/json" \
     -d '{"argv": ["python", "train.py"], "cwd": "C:\\work", "cpu": 4, "ram": 8, "time": "1h"}'
```

## 17. Шпаргалка

```bash
rmq top                                     # что свободно
rmq run --cpu 4 --ram 8 --time 10m -- python script.py
id=$(rmq submit --cpu 8 --ram 16 --vram 6 --time 3h --preempt requeue --name train -- python train.py)
rmq wait $id --timeout 540                  # 124 = ещё работает
rmq wait 12 13 14 --timeout 540             # ждать все: 0 — все успешны
rmq submit --series S ...                   # задачи серии по одной, по порядку; --after ID — после задачи ID
rmq history --task $id --range 2h           # сколько брала задача по времени, колебания нагрузки
rmq past --name chunk                       # прошлые запуски: время, пик ОЗУ, ядра — для следующей заявки
rmq retime $id --time 5h                    # поправить заявку времени на ходу
rmq priority $id high --code СЛОВО          # высокий приоритет — только со словом, которое назвал владелец
rmq queue --pc Стационар                    # очередь другого ПК владельца (только чтение)
rmq status $id                              # состояние и причина ожидания
rmq logs $id --tail 50                      # последние строки лога
rmq cancel $id                              # отменить свою задачу
rmq resume $id                              # продолжить свою задачу с пометкой «зависла»
rmq queue                                   # очередь всех агентов
rmq nodes                                   # ПК вычислительной сети и сколько у них свободно
rmq submit --where auto ...                 # на тот ПК сети, где задача стартует сразу
rmq stats --period 24h                      # статистика менеджера: нагрузка, задачи, температуры
rmq stats --files                           # CSV-файлы статистики; rmq stats --file tasks.csv — один из них
rmq status $id --events                     # все события задачи
rmq whoami                                  # кто я и мои лимиты
rmq start                                   # если менеджер не отвечает
rmq guide                                   # это руководство
```
